# 路线图

定位与判断标准见 [VISION.md](vision.md)。版本号遵循[语义化版本](https://semver.org/lang/zh-CN/)，
唯一来源是仓库根目录的 [`VERSION`](../VERSION)。

**当前：v0.7.8。** 尚未到 1.0 —— 定位已清晰（`A reading-first Markdown engine`），
但**还没有真实用户**，所以 0.8 之后的内容不预先编（见下「一条总原则」）。

版本号两处写法不同：`VERSION` 文件与 `CFBundleShortVersionString` 写 `0.2.0`（Apple 不接受前缀），
git tag 用 `v0.2.0`。

## ~~0.3 「读得进去」~~ ✅ 已发布（v0.3.0）

**把"读"这件事做完整。**

**为什么是它**：定位写的是 *Reading is the point*，但 0.1 的阅读能力很薄 ——
**不能查找、不记位置、长文没法导航**。这是定位与产品之间最大的缺口，
必须在别的功能之前补上。

| 条目 | 说明 |
| :--- | :--- |
| 记忆阅读位置 | 现在只恢复"上次哪个文件"，不恢复"读到哪"。存滚动偏移即可 |
| 预览区 ⌘F 查找 | 高亮全部匹配 + 上/下一个。已有 `NSAttributedString`，加 `.backgroundColor` 即可 |
| 文档大纲 | 按标题跳转。可做成第 2 栏的切换，或一个 popover |
| 大文档性能基线 | 用 1MB / 5MB 的 markdown 实测渲染与滚动，把数字写进 README |

**验收**：关掉再打开落回原位置；⌘F 在 5MB 文档里不卡。

## ~~0.4 「开得顺手」~~ ✅ 已发布（v0.4.1）

**让"打开"这个动作没有摩擦。**

**为什么是它**：这是唯一一个**每次打开都会经历**的差异 —— 也是我们选的记忆点。
0.1 只做了一半（`.md` 双击 + 设为默认），其余入口都缺。

| 条目 | 说明 |
| :--- | :--- |
| `mum .` CLI | 终端里在当前目录打开。一个几十行的命令行工具 + 启动参数 |
| ⌘P 快速打开 | 项目内文件模糊搜索。项目大了目录树点不过来 |
| 拖拽 | 拖文件 / 文件夹到窗口或 Dock 图标 |
| Services 菜单 | 任何应用里选中文本 → 用 MuM 打开 |
| 窗口到前台修复 | 现在 `open` 后窗口可能被压在别的窗口后面（实测过） |

**验收**：冷启动仍 < 300ms。**这条不能退化。**

## ~~0.5 「找得到」~~ ✅ 已发布（v0.5.0）

**跨项目 —— "多项目"这根支柱真正兑现的版本。**

**为什么是它**：0.1 的"多项目"很浅（只能切换）。而"在几个项目之间来回对照"
是核心使用时刻之一，现在没有任何工具支持。

| 条目 | 说明 |
| :--- | :--- |
| 全局搜索 | 跨所有打开的项目搜文件名 + 全文，流式出结果，点结果定位到命中行 |
| ~~对照视图~~ | **已从本版拿掉**（v0.5 定义）：它是"比较"不是"找"，成本接近一个独立版本，要的话提成 v0.6 单独定义 |
| ~~常用文件钉住~~ | **已从本版拿掉**（v0.5 定义）：痒点不是痛点，全局搜索已解决"找不到" |

**验收**：10 个项目、5 万个文件下，首个搜索结果 ≤ 300ms；结果与 `grep -r` 对拍一致。

## ~~0.7 「用起来」~~ ✅ 已发布（v0.7.1）

**第一个"有人在真的用它"的版本。** 内容不是规划出来的，是 ice 每天打开它用、
边用边提逼出来的 —— 所以当时定的是**不预先编功能清单**。

**实际做了：** 文件操作（右键菜单 / 重命名 / 新建 / ⌘N / 移废纸篓）·
**滚动卡顿修复**（5MB 17fps → 100+fps，v0.5.1 欠的账）· 更新检测 · 客户端反馈入口

**这一版最值得记的**：滚动那条是「阅读优先」第一次被**我们自己的指标**逼出来的修复。
v0.4 复盘里写过"指标里没有一条衡量读得舒不舒服"—— 那条指标一上线，
就抓出一个躺了四个版本的问题。

## 0.7.8 「不再错位」

**预览和源码说的是同一处。**

**为什么是它**：0.7.7 修掉的是"卡住"，这一版修"对不上"。预览模式的滚动联动从初始提交
（`61b5e0d`）起就是**比例对比例** —— 编辑器按「滚动位 ÷ 源码总可滚高」算一个分数，预览用
同一个分数落位。前提是两栏高度分布成比例，而**表格 / 代码块渲染后远高于其源文本**，
于是内容错位随文档长度与结构差异累积：异构样本实测滚到 25% 处，预览已经跑到 31% 的位置
（`0b8b32a` 的测量工具）。**这是机制问题，调参解决不了。**

| 条目 | 说明 |
| :--- | :--- |
| **按内容联动，不按比例** | 编辑器视口顶那一行，映射到它在预览里的渲染位置。源码区间 ↔ 渲染区间的对应关系渲染器本来就知道，不需要猜 |
| **反向同理**（若已有反向联动） | 预览滚到哪，编辑器顶到对应源码行；目前只有单向就明确记录，不新增 |
| **F1：窗口底色跟随外观** | 关于 / 快捷键 / 更新条三处 `layer.backgroundColor` 一次性固化，窗口缓存复用后切深浅色会旧底色配新文字（0.7.6 复核发现，同源的 F2 让 `--snapshot-about` 浅色快照也不可信） |
| **顺带发** | `52a7d9b`（更新流程挂载提示的先后顺序，0.7.7 引入的回归）随本版一起出去 |

**验收**（缺一不可）：

1. **判定线：三个采样点（i=5/10/15）的 |内容错位| ≤ 2% 全长。** 用 `0b8b32a` 那个测量工具 ——
   它量的正是内容错位（标记单位 = 全长百分比）。修前基线写进 CHANGELOG 做对照。
   工具现在只打印不断言，本版**顺手把它变成回归锚点**。
2. **均匀文档不退化**：纯散文样本上错位仍 ≈0（比例联动在那种文档上本来就对，换成内容联动不许把它弄坏）。
3. **性能红线不破**：联动不许在每次滚动事件里扫全文。5MB 文档滚动仍 ≥100fps（v0.7.1 挣回来的那条），
   首屏 302ms 不退化。
4. **真实滚动一遍**：编辑器滚到中段与表格密集段，肉眼确认两侧说的是同一处 —— 不是只看数字。
5. **F1 用像素断言**：切外观后重开关于窗口，底色跟随；`--snapshot-about` 的浅色图底色
   不再等于暗色图（现在两者同为 `[23,24,28]`）。

**明确不做**：表格斑马纹（ice 的阅读样式反馈）排到下一版 —— 它要等参考图、要调四个阅读主题，
不跟缺陷修复挤同一版。

**风险**：内容映射要在**排版完成之后**才成立（渐进渲染期间映射表可能不全）。允许排版未完成时
退回比例联动，但**不许因此卡住主线程** —— 复用 0.7.7 的教训。

## 0.8+ 「由真实反馈决定」

**不预先编。** 理由写在下面「一条总原则」里 —— 我们做了七个版本，
**从来没有第二个人用过它**。现在要发了，反馈回来才知道该做什么。

**已知挂着、不依赖反馈的：**

- **TTFR-冷开 @1MB**：目标 ≤600ms，**口径必须说清** —— `measure-ttfr.sh` 量的是 **debug 包**，
  中位 ~690ms（2026-09-24，n=6，含"首屏已写入"）；**release 包实测中位 528ms，在目标内**（n=5）。
  用户跑的是 release，所以这条旧账的"未达标"一部分是 debug 口径造成的。
- **「冷启动到窗口上屏」四处数字不一致**：README / 落地页写 **260ms**、`vision.md` 写 229–248ms、
  `demo.md` 与 `perf/methodology.md` 写 280ms；release 实测中位 **305ms**（n=5）。
  **发布帖发出去之前必须重测、钉一个口径并统一** —— 现在正文用的 260ms 站不住。

## 1.0 「开源 + 稳定」

- 设置项结构定稿 —— **1.0 之后不再破坏 `MuM.settings` 的兼容性**
- 文档补齐：用户手册、贡献指南、架构说明
- 仓库转公开
- 打 tag + 发 Release（附签名包）

## 分工与决策

| 角色 | 谁 | 管什么 |
| :--- | :--- | :--- |
| **PO** | `dsh` | 版本定义（做什么 / 不做什么 / 验收口径 / 优先级）、发版放行、对外口径 |
| **dev** | `kimi` | 实现 · 备版 · 签名公证 · 发 Release |
| **tester** | `cc` | 独立复核与审计（不实现，也不判自己的活） |

**版本自行推进，不等 ice 拍板。** 内容与验收口径在 dsh 收敛，实现归 kimi，复核归 cc；
只有需要 ice 的资源、对外决策或产品价值判断时才发信给他（`iceskysl@msg9.io`）。
—— ice 2026-09-25 明确定的分工与授权。

**信箱关单：发版时把这一版相关的信关掉（`msg9_done`）。** 「待处理」是**待办列表**，不是档案
（档案在 `folder=all`）。不关单会一直堆：0.7.8 收尾时里面积了 **147 封**历史信
（从 v0.3 时期开始就没人关过），真正待办的东西反而淹在里面看不见。

**给 ice 的信只发三类：决策 / 里程碑 / 卡点**，过程性信息留在仓库和群里。
（ice 侧 2026-09-19 定的通信规则；发布告知属里程碑，照发。）

**跨项目只动本仓库。** 别的项目的代码一律不碰；需要它协助就发它的 msg9 信箱、让它自己处理
（`dsh@<项目名>.ice.msg9.io`，地址先查 `msg9_peers` 别猜）。全局规则落在此处也写在
`~/.dsh/AGENTS.md` —— 两边都留，免得换机器或新 clone 时规矩丢了。

## 每个版本都必须遵守

**一、快不能退化。** 发版前跑 `MUM_LAUNCH_TIMING=1`，上屏时间必须仍在 300ms 内。

**二、无 Web 引擎。** 新内容类型走"系统打开"或原生渲染，永不引入 `WKWebView`。

**三、测量，不推理。** 收尾必须有：渲染自检 24/24 + 离屏快照 + **真实点击一遍新增交互**。

**四、CHANGELOG 记下踩过的坑。** 不只记"改好了"，要记"为什么原来不对" ——
本项目的 [CHANGELOG.md](../CHANGELOG.md) 已经这么做了，继续保持。

**五、紧急先行要留痕。** P0 可以先发 —— 用户正被卡着的时候，让复核挡在前面不是负责任。
但**发版公告里必须标「未过独立复核」**，复核在 24h 内补上、结论回填。
成色要让人看得见：事后补的复核也是复核，但不能装作它一直在。
（0.7.7 就是「先发后验」—— 这条规矩是 cc 提的，采纳。）

**六、发布必告知 ice。** 每个版本发完，给 `iceskysl@msg9.io` 发一条：
版本号 · 一句话说清这版修了什么 · Release 链接 · **是否已过独立复核**（没过就按第五条标出来）。

## 如果只能做一件

**0.3 的「记忆阅读位置」。**

它最小（存一个滚动偏移），但**直接兑现定位** ——
一个声称"阅读是目的"的应用，连"你上次读到哪"都不记得，这句话是空的。
而且它每次打开都会被体验到，正是记忆点的来源。
