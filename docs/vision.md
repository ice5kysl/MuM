# MuM 的定位

> **Fast, native, multi-project Markdown reader.**
> **Reading is the point, not a preview.**
>
> 快、原生、多项目的 Markdown 阅读器 —— 阅读是目的，不是编辑的副产品。

这份文档回答**为什么**。具体做什么、什么时候做，见 [ROADMAP.md](roadmap.md)。

---

## 一句话里的三个词，各自有实测撑着

| | 主张 | 证据 |
| :--- | :--- | :--- |
| **Fast** | 没有启动画面这回事 | 进程启动到窗口上屏 **280ms**，渲染本身 **0.03s**（`MUM_LAUNCH_TIMING=1` 可复现） |
| **Native** | 2.8 MB，全程没有 Web 引擎 | cmark-gfm 解析成 `NSAttributedString`，排版与绘制全在 AppKit 里手写 |
| **Multi-project** | 项目是主语 | `⌘1`…`⌘9` 秒切，项目回答"我在哪" |

第三句是界限：**在别处，阅读是编辑的副产品** —— `preview` 这个词本身就是证据，
它暗示"真正的工作是写，看只是顺便"。MuM 反过来。

---

## 为什么是这个定位

### 它解释了我们做对的每一件事

三栏布局（左＝我在哪，右＝那是什么）、项目是一等公民、`⌘1`…`⌘9` 秒切、
阅读主题只改纸色而不动应用外观、HTML 交给系统打开而不是自己渲染 ——
这些决定看起来分散，其实都是同一句话的推论。

### 它划清了和邻居的界

|  | 给你**位置** | 给你**内容** |
| :--- | :---: | :---: |
| Finder | ✅ | ❌ |
| Markdown 编辑器 | ❌ | ✅ |
| **MuM** | ✅ | ✅ |

### 它的护城河是架构，不是功能

"功能多"是能追的，**"架构上不一样"追不了**。

- 没有 Web 进程 → 没有白屏、没有字体回退、没有滚动不同步
- 代价是每个排版效果都得自己实现（引用块竖线、分隔线、代码块底色、GFM 表格全是手绘的）

---

## 判断标准

新功能该不该做，按顺序问这三个问题：

1. **它让"读"更容易，还是只是让"编"更方便？** 后者优先级永远低于前者。
2. **它会拖慢启动、变大体积、或引入 Web 引擎吗？** 会，就不做。
3. **它属于"位置"还是"内容"？** 两者都不是的（云同步、账号、协作），不做。

---

## 明确不做

| | 原因 |
| :--- | :--- |
| **HTML 渲染** | 要么引入 `WKWebView`（毁掉护城河），要么永远追不上浏览器。**交给系统打开** |
| 插件系统 | 和「安静的工具」冲突，还要维护一套 API |
| 云同步 / 账号 | "无账号、无上报"是资产，引入账号就引入遥测 |
| WYSIWYG 编辑 | 那是写作工具的路，和"阅读是目的"对立 |
| 移动端 | Clearly 在那条线上，打不过 |

---

## 代价，写在明处

**「快」必须一直是真的。** 一旦某次启动变慢、某个操作卡顿，定位就崩 ——
它比"功能多"难维持得多。所以每次发版前必须复测启动时间，这是唯一不能妥协的指标。

**气质是「安静的工具」。** 没有欢迎页、没有引导、没有"功能发现"、没有成功提示。
要做到这一点，得一直忍住不往界面上加东西。

---

## 两条工作准则

这两条不是口号，是这个项目实际踩出来的。

**一、测量，不要推理。**

本项目至今真正的突破，全部来自"量一下"而不是"想一下"。同一个坑反复出现过五次：

| 我推的 | 实际 |
| :--- | :--- |
| 行号画在容器左边距里 | 被 `NSLayoutManager` 的裁剪区裁掉 |
| 状态栏底色会跟着外观刷新 | 回调没触发，停在浅色 |
| 语义色在浅底深底都可读 | 纸色脱离应用外观后就失效 |
| 冷启动 1.24 秒 | 那是离屏路径的耗时，真实 280ms |
| M 按路径端点算居中 | 斜接尖刺把视觉重心抬高了 |

**当你发现自己在推理渲染结果而不是测量它的时候，停下来写个测量工具。**

**二、"构建成功"不等于"跑起来了"。**

`swift build` 通过、离屏快照能渲染 —— 都不代表用户点得动。
每个版本收尾必须真实点击一遍新增交互，并把启动时间复测一次。
